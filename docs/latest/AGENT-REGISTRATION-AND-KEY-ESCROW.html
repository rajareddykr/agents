Supersedes one claim in agent-identity-product-overview.md. That document says the mesh identity is "short-lived (per-process) — agents may rotate DIDs". That is no longer true and was the problem this work fixed. A governed agent now keeps one DID for its whole life. Treat this document as authoritative on identity lifetime.

1. The one-paragraph summary#

An operator registers an agent once and receives a long-lived credential. The agent generates its own keypair on first start, derives a DID from the public half, and escrows the encrypted private key with the control plane. Every restart recovers that key and comes back with the same DID, so trust score, drift history and policy bindings survive. Previously an agent got a new identity on every restart, and everything attached to the old one was orphaned.

2. What changed, and why it mattered#

The old flow — bootstrap tokens#

Operator   mint a bootstrap token        (single-use)
Agent      start  -> consume token -> generate keypair -> NEW DID
Agent      restart-> token already consumed -> needs a NEW token -> NEW DID again

The token was an enrolment secret, but agents re-enrolled on every restart. Consequences seen on real deployments:

Symptom Consequence
A new DID per restart Trust score reset to zero each time
A new epoch per restart Drift history orphaned; policy bindings pointed at a dead epoch
One live CP showed 15 DID epochs for a single agent Fleet counts inflated; "how many agents do I have" unanswerable
A hand-minted token per restart Ops toil, and tokens shared by copy-paste
BootstrapTokenCreate carried no agent name Any valid token could claim any agent — a live spoofing hole

Extending the token TTL could not fix this: single-use was a property of the schema (consumed_at), and the missing name binding was a separate defect.

The new flow — register once, escrow the key#

Operator   Register Agent (UI)  ->  long-lived credential, shown ONCE
Agent      first start          ->  generate keypair -> attach public key -> escrow private key
Agent      every restart        ->  same credential -> recover key -> SAME DID

A restarting agent calls nothing in place of "consume a bootstrap token". It already holds a durable credential. If a question starts "what does the agent bootstrap with on restart…", it has taken a wrong turn.

Side by side#

Old (bootstrap) New (register + escrow)
Operator action per restart mint a token none
Credential lifetime single use 1 year, rotatable, revocable
DID across restarts new every time same
Trust score across restarts reset preserved
Drift history / policy bindings orphaned preserved
Agent name binding absent (spoofable) enforced
Private key on restart regenerated recovered from escrow
Who holds the private key agent only (then lost) agent only; CP holds ciphertext
Epoch count per agent grows on every restart stays at 1

3. The three secrets, and what each one does#

This is the part most often misunderstood. Three different things, three different jobs.

Secret Env var Job Reaches the CP?
Agent credential AGT_AGENT_TOKEN Authenticates the agent Yes — it is a CP credential
Org passphrase AGT_AGENT_PASSPHRASE Encrypts / decrypts the private key Never
Operator / service token AGT_CP_TOKEN Operator and service calls Yes

Rules that follow from this, and that QA should test rather than trust:

  • The credential authenticates; the passphrase decrypts. Neither alone yields a private key. Steal the credential and you get ciphertext. Steal the passphrase and you cannot fetch the blob.
  • AGT_AGENT_PASSPHRASE is organisation-wide and host-local. It is minimum 32 characters, and it is never transmitted or logged. A total control-plane compromise therefore yields ciphertext, not keys.
  • The flow activates when either variable is set, then requires both. This is deliberate: gating on the passphrase alone would let "token set, passphrase forgotten" fall silently back to the legacy path and re-identify the agent on every restart.

4. What a DID is, and why it is stable now#

DID = "did:mesh:" + sha256(public_key)[:24]

The DID is a cryptographic commitment to the public key — not a database record. That has two consequences worth internalising:

  1. Same key ⇒ same DID. Recovering the key from escrow is what makes the identity stable. Nothing looks the DID up; it is recomputed from the key.
  2. A different key ⇒ a different DID, always. There is no way to "keep" a DID while changing the key. This is why the identity key never rotates — see §7.

Known wrinkle, worth knowing before you read older code. Two DID schemes exist in the tree. AgentDID.generate() builds a 32-character DID from name + org + nonce; the governed path uses the 24-character sha256(public_key). The SDK deliberately never calls AgentIdentity.create() for this reason. Unifying them is outstanding.

5. The registration flow, step by step#

Step 1 — Operator registers the agent#

POST /api/v1/orgs/{org}/agents/provision (operator, JWT) — the UI's Register Agent button.

Returns, once:

Field Meaning
credential the agt_… value — displayed once, never retrievable
credential_id handle for rotate/revoke
logical_agent_id the durable identity of the agent as an operator thing
expires_at ~1 year out by default
trust_ceiling caps the trust score this agent can reach
already_existed true if the name was already registered — the previous credential is still live

No DID and no key material exist at this point. Registration creates the logical agent and the credential that authorises it. The agent has never run.

Two things deliberately absent from the form:

  • sponsor email — read from the operator's session instead of typed. The sponsor is whoever clicked Register.
  • capabilities — declared by the agent at attach, where they are true rather than aspirational.

Step 2 — First start: keypair, attach, escrow#

The agent, configured with AGT_AGENT_TOKEN + AGT_AGENT_PASSPHRASE:

  1. Generates an Ed25519 keypair in its own process. The private half never leaves it in plaintext.
  2. Computes its DID from the public half.
  3. POST /orgs/{org}/agents/identity — attaches the public key. The CP signs the sponsorship credential (VC) here, opens an epoch only if the DID is new, and records the operator who registered it.
  4. Encrypts the private key locally — HKDF-SHA256 from the org passphrase, then AES-GCM — and PUTs the ciphertext to escrow.

Order matters: attach happens before escrow. A blob for an identity the CP never accepted would just be recovered and attached one restart later.

The sponsorship VC is signed at attach, not at registration. It commits to a public key that does not exist until first boot. The operator's assurance is preserved: it is recorded on the credential at registration and read back at attach.

Step 3 — Every restart: recover and carry on#

  1. Fetch its own escrow blob. The GET takes no name and no DID — a caller receives only its own ciphertext and cannot express "somebody else's".
  2. Decrypt with the org passphrase → the original private key.
  3. Recompute the DID → identical.
  4. Attach → new_epoch=false, epoch_count unchanged.
  5. Escrow is not rewritten. key_escrowed_at stays put.

6. Escrow: how the key is protected#

Property Value / behaviour
Key derivation HKDF-SHA256, reported as hkdf-sha256-v1
Cipher AES-GCM
Salt and AAD the logical agent handle `org
Keyed on the logical agent (org, name)
Stored by the CP ciphertext only

Why keyed on (org, name) and not something more obvious:

  • Not the DID — the DID is derived from the key being recovered, so it is the thing you do not yet have at restore time.
  • Not the credential — credentials rotate; the identity must not.

That choice is what makes rotation safe: the credential changes and the identity does not.

Why the handle is also the AAD: the passphrase is shared org-wide, so the handle is what separates agents. A blob lifted from one agent's row fails to decrypt as another's even for a holder of the org passphrase.

Access control: a credential is bound to an agent through the agent_credential_bindings side table. Absence of a binding row is a denial. There is deliberately no api_tokens.agent_id column — a nullable column would match anything and open every operator token onto every agent's blob.

7. What never happens (and why the rules exist)#

  • The identity key never rotates. KeyRotationManager rotates signing keys only. The identity key the DID commits to is created once at enrolment and replaced only by re-enrolling. Escrow is written at exactly two moments — first boot and re-enrolment — and neither is a rotation. Why: rotation preserves the DID while replacing the key, but the DID is sha256(public_key). Escrowing a rotated key would mean the next restart recovers a key deriving an identity the CP has never seen — a new epoch, trust and drift and bindings gone, presenting as a clean start. A guard refuses to store a key that does not hash to the agent's DID.
  • The CP never sees a private key or the passphrase.
  • The operator view never returns ciphertext. An operator holds the credential but not the passphrase; handing them ciphertext moves key material somewhere it has no reason to be.
  • Two agents can never share a DID. A DID already held by a different logical agent is refused 409, never repointed — two agents on one DID would mean two agents holding one private key.

8. Failure behaviour — what fails open, what fails closed#

This table is the single most useful thing on this page for Ops.

Situation Behaviour Why
Wrong passphrase Fail CLOSED — KeyRecoveryFailed, agent does not start, existing blob untouched Running as a different agent is worse than not running
Wrong passphrase with fail_mode=open Still fail closed fail_mode=open means "run ungoverned rather than not at all". It has never meant "run as a different agent". KeyRecoveryFailed is a separate exception class precisely so fail_mode cannot reach it
Escrow write fails on first boot Fail OPEN — agent runs, logs a loud warning A failed backup costs the next restart a new DID. A failed startup costs the agent entirely. The first is recoverable
Credential revoked / rotated away Refused. Error says "This is the credential, not the passphrase" Escrow fetch is the first call a credential makes, so all credential faults used to surface as "could not fetch the escrowed key" and sent operators to check a healthy passphrase
agent-mesh not installed Agent runs; warns that escrow is unavailable and the next restart will mint a new DID Never silent
Passphrase shorter than 32 chars Refused at construction HKDF stretches a passphrase, it does not create entropy
Control plane unreachable at restart Fail closed on key recovery Same reasoning as a wrong passphrase

9. Lifecycle operations#

Rotate a credential#

POST /orgs/{org}/agents/{id}/credential/rotate — issues a new credential and revokes the rest. The agent keeps its DID: escrow is keyed on (org, name), not on the credential. The old credential is refused immediately. The agent keeps running until it next authenticates — update its config now.

Revoke a credential#

DELETE /orgs/{org}/agents/{id}/credential — revokes every credential bound to the agent.

Revoke is a stop button, not a delete button. The escrowed key survives revocation. Re-register the same name, issue a fresh credential, and the agent returns with the same DID and its history intact.

Also: the control plane cannot terminate a remote process. A revoked credential locks the agent out at its next authentication. To cut off a running agent immediately, use the kill switch, which also revokes the DID so peers refuse it.

Revoke an identity (a different action)#

POST /identity/{id}/revoke — revokes the DID, adds it to the org revocation list, and suspends the agent. Reactivate to undo. Do not confuse it with credential revoke: the UI now labels them Revoke Identity and Revoke credential.

10. Observability — "will this agent survive a restart?"#

GET /orgs/{org}/agents/{logical_agent_id}/enrolment (operator) answers it.

It returns facts, not a verdict — the control plane records, it does not derive. The UI composes the verdict.

Field Use
live_credential_count can it authenticate at all?
credential_expires_at / credential_issued_at credential health
key_escrowed, key_id, key_escrowed_at, kdf can it recover its identity?
epoch_count has it ever started?

Both halves are needed, because either alone answers the wrong question:

  • live credential + no escrowed key → runs today, comes back as a new DID
  • escrowed key + no live credential → cannot start, but its identity is intact

The five states an operator sees#

State Facts Meaning
Survives credential + key keeps DID, trust, drift, bindings
Awaiting first start credential, no key, epoch_count=0 normal between registering and deploying
NEW DID on restart has an identity, nothing escrowed ⚠️ runs fine today, silently replaces itself on next restart
Stopped, recoverable key, no live credential re-register the same name to bring it back
Not enrolled neither pre-feature or never set up

epoch_count exists to separate rows 2 and 3. They report the same two facts and mean opposite things — a fresh registration has no identity to lose; an agent whose escrow failed is about to lose one. Without it, the UI warned on every fresh registration, which is how operators learn to ignore the warning that matters.

"NEW DID on restart" is the state this observability exists for. It is invisible on every other screen: the agent is healthy, heartbeating, passing policy — and one restart from losing everything that makes it that agent.

11. Ops runbook#

Deploying this#

  • Migrations: 0028_bootstrap_token_agent_name → 0029_agent_key_escrow → 0030_logical_agent_trust_ceiling. New tables agent_key_escrow and agent_credential_bindings; new column logical_agents.trust_ceiling.
  • The chain builds from scratch on Postgres. (An old note about "cannot build from scratch" applies to SQLite only — do not generalise it.)
  • The SDK ships via the wheelhouse. Rebuild it after any SDK release, and install offline with --no-index --find-links <abs path>.

Setting up an agent host#

  1. Set AGT_AGENT_PASSPHRASE — one value per organisation, ≥32 chars, stored where host secrets normally live. Losing it means every agent on that host mints a new DID on next restart.
  2. Register each agent in the UI; put the credential in that agent's config.
  3. Start the agent once and confirm the UI reports Survives.

Things that will bite you#

Symptom Cause
Secret decryption failed: InvalidTag at CP startup The database was written with a different SECRET_KEY. Not a code fault — check the key before filing a bug
Agent mints a new DID every restart AGT_AGENT_PASSPHRASE missing/changed, or agent-mesh not installed so escrow never ran
403 URL org code does not match the authenticated tenant The org in the URL does not match the caller's org
Fleet counts drift while idle IMPL-066's liveness sweep revokes stale epochs. Expected; read counts fresh
Agent refused right after a rotate It is still using the old credential — update its config

Storage tiers (forward-looking)#

Four tiers exist in preference order — HSM, cloud KMS, TPM, escrow. Only escrow is implemented; 1–3 are detection stubs. Two rules matter operationally:

  • An operator lock is a lock. AGT_KEYSTORE_TIER=kms on a host with no KMS refuses to start rather than quietly using a weaker tier.
  • A recorded tier is sticky. If a host loses its TPM the agent refuses rather than re-resolving down to escrow — coming up on a weaker tier would mean a new identity presented as a clean start. Deleting the state file is the deliberate re-enrolment, and the error says so.

Auto-probing never selects an unimplemented tier: a host that merely has a PKCS#11 library must not be taken down by it.

The assertions that matter most#

  1. Three starts in three separate OS processes → one DID, epoch_count stays
    1. Separate processes matter: nothing can be carried in memory, so a stable DID proves recovery from escrow.
  2. Wrong passphrase fails closed, mints no DID, and does not overwrite the stored blob — and the correct passphrase still works afterwards.
  3. Rotation keeps the DID; the old credential is refused.
  4. Revoke preserves the escrowed key; re-registering the same name restores the same DID.
  5. Cross-agent isolation: agent A's credential declaring agent B's name is refused.
  6. The operator view never contains ciphertext.
  7. A UI-issued credential actually boots an agent which then survives a restart. Displaying a credential is not the same as it working.

Testing rules learned the hard way#

  • Test through the API or the UI, never SQL. A SQL check can pass while the API that exposes it is broken.
  • Do not instrument the app to make a test pass. No DOM injection, no assigning .value. If a control cannot be driven as a user would, that is a result.
  • Assert HTTP status, not just body fields. A correct 422 looks like a missing field if you only read meta.total.
  • Compare failing test sets, not counts. A total can match while the membership differs.
  • X-Auth-Info is trusted on network isolation by design. Do not write it up as a cross-tenant leak; the real boundary is the URL org versus the agent's org.

13. Migration reality, stated plainly#

Migrating existing agents cannot preserve their identities. Agents enrolled under bootstrap hold no durable credential and no escrowed key, and their private keys are gone from the processes that made them. Each one gets one new DID — the last it will ever get. "Retiring bootstrap" sounds lossless and is not.

Also true during the transition:

  • Bootstrap still works, now name-bound, and logs a deprecation warning.
  • Agents predating this feature show Not enrolled and will keep re-identifying until re-registered.
  • Sponsorship assurance drops from "the agent proved possession of a secret" to "an operator asserted this agent exists". That is a deliberate trade and is documented rather than hidden.
  • Removing bootstrap entirely is gated on a query proving every agent has been re-registered.
